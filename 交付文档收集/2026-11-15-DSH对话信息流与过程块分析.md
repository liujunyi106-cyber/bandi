# DeepSeek Harness 对话流式信息流与过程块渲染 —— 技术分析报告

> 分析对象：`D:\源码\各Agent源码\deepseek-harness\`（TypeScript / Cordis 插件框架）
> 对比对象：bandi `frontend/src/components/chat/`
> 性质：**只读分析**，未修改任何文件
> 结论标注：每条论断附 `file:line`；无法确证处标「未验证」

## 摘要（先看这 5 条）

1. **DSH 的过程展示不是"一个过程块"，而是"事件日志的线性投影"**。一条 assistant 输出被拆成若干 `block`，按 `chunk.index` 稳定排序；工具调用是独立节点，按 `tool/call` 事件的 `seq` 插入**总时间线**。所以"读文件 → 结果 → 改文件 → 跑命令"天然按真实执行顺序排列。
2. **顺序的唯一真相是 `anchorSeq`（事件序号）**。渲染前对所有节点做一次 `sort((l,r) => l.anchorSeq - r.anchorSeq || l.key.localeCompare(r.key))`（`chat-snapshot-builder.ts:138`）。这不是"按类别分组后排序"，是**先排好序再逐行渲染**。
3. **DSH 没有"过程块"这个容器组件**。每一行（Think 行 / Tool 行）各自独立折叠，`DisclosureRow` 是 24px 单行 chrome（`DisclosureRow.tsx:6-26`）。不存在"总行 → 分类行 → 明细行"三级嵌套。
4. **工具卡片类型由服务端决定**：工具自己声明 `presentCall`/`presentResult`，返回 `ToolCallView`/`ToolResultView` 这套 provider-neutral 词汇（`packages/core/tools/src/presentation.ts:46,140`），前端按 `card` 判别式切换 Terminal/Diff/Read/Search/Web 卡片。前端**不靠工具名字符串猜**。
5. **bandi 的根因是"先分类后渲染"**：`buildBuckets()` 把 `ProcessNode[]` 按 `bucketFor(toolName)` 重新分组（`ProcessBlock.tsx:69-115` + `process-display.ts:142-152`），跨类别的时序在这一步被永久丢弃；且 `ProcessNode` 类型**根本没有顺序字段**（`chat-store.ts:18-108`）。

## ① 数据模型

### 1.1 三层结构：ContentBlock → AssistantBlock → 渲染行

DSH 的 assistant 内容走三次形态转换：

| 层 | 类型 | 定义位置 | 用途 |
|---|---|---|---|
| 核心 | `ContentBlock[]` | `packages/llm/llm/src/types.ts`（core LLM 层） | 模型原始输出 |
| 投影 | `AssistantBlock[]` | `client/runtime/.../conversation.ts:44-49` | UI 分类 |
| 渲染 | React 行数组 | `AssistantMarkdown.tsx:52-101` | 逐块渲染 |

`AssistantBlock` 是 5 元判别联合（`conversation.ts:44-49`）：

```ts
export type AssistantBlock =
  | { kind: 'text'; text: string }
  | { kind: 'reasoning'; text: string }
  | { kind: 'image'; attachment: ImageAttachmentRef }
  | { kind: 'tool-call'; callId: string; name: string; argsRaw: string }
  | { kind: 'other'; block: unknown }
```

转换函数 `toAssistantBlock` 在 `conversation.ts:65-73`，按 `block.type` 一一映射。

**关键：`AssistantBlock` 本身没有顺序字段。** 顺序完全由**数组下标**承载（见 §1.3）。

### 1.2 顺序索引：`chunk.index` 是权威

`StreamChunk` 的每个 delta 都带 `index`（`packages/llm/llm/src/types.ts:291-303`）：

```ts
export type StreamChunk =
  | { type: 'block-start'; index: number; blockType: ContentBlockType }
  | { type: 'text-delta'; index: number; text: string }
  | { type: 'reasoning-delta'; index: number; text: string }
  | { type: 'tool-call-delta'; index: number; id: CallId; name?: string; argumentsDelta: string }
  | { type: 'block-end'; index: number; block: ContentBlock }
  | { type: 'usage'; usage: TokenUsage }
  | { type: 'finish'; reason: FinishReason; replayState?: unknown }
```

注释明确写出设计意图（`types.ts:284-289`）：**"Block indexes correlate interleaved deltas, and `block-end` carries the assembled block."**

即：**index 是 URL 路径，不是到达顺序**。乱序到达的 `block-start` 先占住 index 位置，后续 delta 填进同一格。

### 1.3 稀疏数组 + 压实 = 稳定渲染序

`PartialAccumulator`（`client/runtime/.../partial.ts:23-103`）是核心累积器：

```ts
// partial.ts:25 —— 注释直说这是故意的稀疏数组
private blocks: (AssistantBlock | undefined)[] = []
```

写入按 index 定位（`partial.ts:50-83`），读取时压实（`partial.ts:96-101`）：

```ts
toPartial(): PartialAssistant {
  if (this.changed) {
    // Compact sparse indexes (out-of-order block-start) into render order.
    this.snapshot = {
      turn: this.turn, step: this.step,
      blocks: this.blocks.filter((b): b is AssistantBlock => b !== undefined),
    }
    this.changed = false
  }
  return this.snapshot
}
```

**这就是"按执行顺序线性展示"的第一层保障**：无论 delta 怎么乱序到达，`filter` 后数组下标序 = `chunk.index` 序 = 模型真实输出序。

`ui-conversation` 侧有一份等价实现 `updateChunk`（`conversation-nodes/assistant.ts:80-132`）+ `compactBlocks`（`assistant.ts:53-55`）。注意这是**两份并行实现**（runtime 的 `PartialAccumulator` 与 ui-conversation 的 `AssistantState`），逻辑一致但未共享代码。

### 1.4 消息节点：`turn` + `step` 双坐标

`AssistantMessageNode`（`conversation.ts:96-118`）：

```ts
export interface AssistantMessageNode {
  kind: 'assistant'
  seq: number          // 事件日志序号 —— 排序权威
  messageId?: MessageId
  time: number
  turn: number         // 用户轮
  step: number         // 轮内模型步（一次 LLM 调用 = 一步）
  blocks: readonly AssistantBlock[]
  usage?: unknown
  provenance?: AssistantProvenanceView
  requestConfig?: AssistantRequestConfig
  timing?: AssistantTiming
  interrupted?: true   // 中断冻结的部分输出
}
```

**`turn`/`step` 的语义**：一次用户请求 = 一个 `turn`；turn 内每次调模型 = 一个 `step`。所以「调工具 → 看结果 → 再想」在数据上是**多个 step**，每次 step 产出一条 `AssistantMessageNode`。

这一点至关重要，也是 DSH 与 bandi 最大的结构差异 —— 见 §6.2。

### 1.5 工具节点：`ToolCallBlock` 递归树

`conversation.ts:294-310`：

```ts
export interface RunningToolCall {
  callId: string
  name: string
  argsRaw: string
  turn: number
  step: number
  time: number
  callView: ToolCallView | null      // 服务端下发的渲染意图
  subCalls: readonly ToolCallBlock[] // 子调用（递归）
}

export type ToolCallBlock = RunningToolCall | ToolResultNode
```

`ToolResultNode`（`conversation.ts:184-204`）多出：

```ts
  call: { name: string; argsRaw: string } | null  // 回填的调用头
  callTime: number | null                          // 配对调用的时间（算耗时）
  content: readonly ContentBlock[]
  isError: boolean
  error?: { name: string; code: string }
  callView: ToolCallView | null
  resultView: ToolResultView | null
  subCalls: readonly ToolCallBlock[]
```

**注意 `call` 可为 `null`**（`conversation.ts:190-191` 注释）：窗口截断导致 `tool/call` 落在窗口外时，仍能渲染结果卡片（只显示 callId）。

### 1.6 完整节点联合

`ConversationNode`（`conversation.ts:280-292`）共 11 种：

```ts
export type ConversationNode =
  | UserMessageNode | AssistantMessageNode | SteeringMessageNode
  | ContextMessageNode | ModelRetryNode | TurnErrorNode | TurnMaxTokensNode
  | ToolResultNode | CommandNode | CompactionSummaryNode | UnknownSurfaceNode
```

`seq` 是 React key（`conversation.ts:280` 注释："kind discriminates; seq is the React key"）。

## ② 流式事件协议

### 2.1 事件序列

DSH 用**append-only 事件日志**（session log），不是"状态帧"。核心执行事件由 `agent-loop` 按固定顺序 append：

| 事件 | 位置 | 语义 |
|---|---|---|
| `turn/start` | `agent-loop/src/agent.ts:255` | 用户轮开始 |
| `step/start` | `agent.ts:279` | 模型步开始 |
| `assistant/chunk` | `agent.ts:349` | 流式 delta 批次 |
| `tool/call` | `agent-loop/src/tool-calls.ts:263` | 工具调用发起 |
| `tool/result` | `tool-calls.ts:281` | 工具结果返回 |
| `step/end` | `agent.ts:292` | 模型步结束 |
| `turn/end` | `agent.ts:319` | 用户轮结束 |

### 2.2 顺序约束是**硬不变式**，由 invariant 插件强制

`packages/core/session/src/invariant.ts` 逐事件校验（这是权威定义）：

| 约束 | 代码位置 | 具体规则 |
|---|---|---|
| seq 严格递增 | `invariant.ts:60-62` | `if (event.seq <= trace.lastSeq) fail(...)` |
| turn 不嵌套 | `invariant.ts:72-82` | `turn/start` 时 `openTurn` 必须为 null；turn 号必须连续 |
| step 不嵌套 | `invariant.ts:94-106` | `step/start` 时 `openStep` 必须为 null；step 号必须连续 |
| step 必须在 turn 内 | `invariant.ts:95-97` | `step/start` 的 turn 必须等于 openTurn |
| tool/result 必须有配对 | `invariant.ts:127-143` | `pendingCalls.has(callId)` 否则 fail |
| step/end 清空 pending | `invariant.ts:107-113` | `pendingCalls = { kind: 'clear' }` |

`tool/result` 的配对校验（`invariant.ts:136-141`）：

```ts
requireOpenStep(trace, 'tool/result', event.data.turn, event.data.step, fail)
const callId = event.data.message.source.callId
const syntheticNotStarted = event.data.message.content[0].isError === true
  && event.data.error?.code === TOOL_NOT_STARTED
if (!trace.pendingCalls.has(callId) && !syntheticNotStarted) {
  fail(`tool/result for ${callId} with no prior tool/call in this step`)
}
```

**这是 DSH 可靠性的地基**：协议不允许出现"结果先于调用"或"孤儿结果"，前端因此可以无条件信任 seq 排序。

### 2.3 前端如何消费：增量投影 + 按帧发布

前端不是"收到帧就 setState"，而是把事件流**投影成 ViewNode 快照**：

1. **匹配**：每个业务模块注册一个 `ConversationNodeDefinition`，声明 `match(event)` 返回 `{id, role}`（`assistant.ts:247-257`、`tool.ts:239-251`）。
2. **累积**：`role: 'start'` 建状态，`role: 'update'` 更新状态（`assistant.ts:258-277`）。
3. **投影**：`buildViewNode` 输出 `{kind, anchorSeq, data, visibility}`（`assistant.ts:296-308`）。
4. **排序**：全局按 `anchorSeq` 排序（`chat-snapshot-builder.ts:135-139`）。

发布节流由 `publication` 声明（`assistant.ts:278-283`）：

```ts
publication: (match) => {
  if (match.event.type === 'step/start') return 'none'
  if (match.event.type !== 'assistant/chunk') return 'immediate'
  const type = match.event.data.chunk.type
  return type === 'usage' || type === 'finish' ? 'none' : 'animation-frame'
}
```

**即：一帧一个 batch（`animation-frame`），usage/finish 不触发重渲染**。这是流式性能的关键设计。

### 2.4 anchorSeq：节点在总时间线的插入点

| 节点类型 | anchorSeq 取值 | 代码 |
|---|---|---|
| assistant-step | 定稿时 `assistant/message.seq`；运行中取首个可见 chunk 的 seq | `assistant.ts:225` |
| tool-call | **`tool/call` 事件的 seq** | `tool.ts:265-267` |
| user / context / command | 自身事件 seq | `chat-snapshot-builder.ts:170` |

`tool.ts:265-267`：

```ts
const anchor = context.start?.event.seq
  ?? ('kind' in state.root ? state.root.seq : context.matches[0]?.event.seq ?? 0)
```

**因为 anchor 是 `tool/call` 的 seq（不是 result 的 seq），工具行在时间线上的位置 = 工具开始执行的位置**。这正是"读文件 → 结果 → 改文件"能按真实顺序排列的机制。

## ③ 过程块渲染

### 3.1 没有"过程块"容器

DSH 的渲染入口 `ChatView`（`chat/ChatView.tsx:146`）拿到一个**已排序的 key 数组**：

```ts
const order = useSession(s => s.chat.order)   // ChatView.tsx:150
const nodeStore = useSession(s => s.chat.nodes) // ChatView.tsx:151
```

然后逐 key 分发到 keyed slot（`ChatView.tsx:143-145` 注释："each ordered business Node crosses the keyed renderer seat"）。

**没有"把多个节点合并成一个过程块"这一步。** 每个节点就是一行。

### 3.2 assistant-step 内部：按块序渲染

`AssistantMarkdown`（`chat/AssistantMarkdown.tsx:37-110`）遍历 `blocks` 数组：

```ts
for (let i = 0; i < blocks.length; i++) {
  const block = blocks[i]
  if (block === undefined) continue
  switch (block.kind) {
    case 'text':      rendered.push(<MarkdownText key={i} ... />); break
    case 'reasoning': rendered.push(<ReasoningRow key={i} ... />); break
    case 'image':     /* 连续图片合并为一个 gallery，见下 */ break
    case 'tool-call': break   // ← 不在这里渲染
    default:          rendered.push(<JsonBlock key={i} ... />)
  }
}
```

**`key={i}` = 数组下标 = chunk.index 序**（`AssistantMarkdown.tsx:60,69`）。

图片块的特殊处理（`AssistantMarkdown.tsx:71-87`）：**连续** image 块合并成一个 `ImageGallery`，key 取组内第一块的 index（注释 74-76 解释：流式追加时只增长 `images` 而不 remount）。

### 3.3 tool-call 块的"跳过"是关键设计

`AssistantMarkdown.tsx:88-90`：

```ts
// Grouped into tool rows by ChatView; hasVisible above skips an empty shell.
case 'tool-call':
  break
```

同时 `hasVisible` 判断（`AssistantMarkdown.tsx:48-51`）：

```ts
const hasVisible = streaming || interrupted === true
  || blocks.some(block => block.kind !== 'tool-call')
if (!hasVisible) return null
```

**含义**：一个只含 tool-call 块的 assistant-step 节点渲染为 `null`（不占高度），工具行由独立的 `tool-call` 节点渲染。

那么"工具行出现在文本中间"是怎么实现的？靠 **anchorSeq 交错**：

- assistant-step 的 anchor = 该 step 的 `assistant/message.seq`
- tool-call 的 anchor = `tool/call.seq`

由于 `tool/call` 在 `step/end` 之前 append（`tool-calls.ts:263`，在 step 内），而 `assistant/message` 的 seq 也在这个 step 内，两者按真实发生顺序交错。

**已验证顺序**（`agent-loop/src/agent.ts:381-399`）：

```ts
this.session.append('assistant/message', {...})       // :381 —— 先定稿文本
if (finish.kind === 'max-tokens') return { kind: 'max-tokens' }
const toolCalls = message.content.filter(b => b.type === 'tool-call')
if (toolCalls.length === 0) return { kind: 'completed' }
const { concluded } = await executeToolCalls(...)     // :395 —— 后执行工具
```

**即：同一 step 内 `assistant/message.seq` 恒早于 `tool/call.seq`**，因此视觉顺序是「本步文本 → 工具行」，符合直觉。

⚠️ **一个真实存在的视觉细节**（不是 bug，是设计取舍）：assistant-step 节点的 anchor 是 `assistant/message.seq`，而该事件是 **step 结束时一次性 append** 的（`agent.ts:381`，在流式 chunk 全部结束之后，`:349` 才是 chunk）。因此流式过程中文本是随 chunk 就地更新的，但**一旦这一步结束、下一步的工具开始执行，文本节点会"锚定"到 message 事件的位置**。同 step 内不会错位（因为 tool/call 在其后），但跨 step 的相对顺序依赖各自 message 的 seq —— 这是正确的。

### 3.4 工具行：单行摘要 + 展开体

`ToolRow`（`ui-tool/.../components/ToolRow.tsx:1-18` 文件头注释，这是最好的规格说明）：

> "ToolRow: the single-line tool summary row — 16px leading slot (state dot / tool icon, chevron on hover or expanded) + title + separator dot + FILL-truncated summary, drawn through the shared DisclosureRow chrome with the whole row as the expand toggle. **The collapsed row is always one line**; every row with body, output, or a card material (terminal, diff, read, search, web) is expandable; **the summary stays inline while open**."

结构（`ToolRow.tsx:196-233`）：

```
[图标/状态点] [标题] · [摘要]        ← DisclosureRow 头部
[展开体：IN/OUT 卡片 或 Terminal/Diff/Read/Search/Web 卡片]
```

`keepContentWhenOpen`（`ToolRow.tsx:207`）保证展开后摘要仍内联显示，不跳动。

### 3.5 行高约束

- 折叠态：**恒一行**（`ToolRow.tsx:6` 注释）
- 展开体：`max-height` 滚动容器，不撑爆消息流（`ToolRow.tsx:11-13` 注释："lives in a max-height scroll container so a long payload scrolls internally instead of taking over the message flow"）
- 卡片默认全部收起（`ToolRow.tsx:13` 注释："Every card kind starts collapsed, so a run of tool calls stays scannable"）

## ④ 工具调用展示

### 4.1 服务端声明渲染意图（这是 DSH 最值得借鉴的架构）

工具实现 `ToolDefinition.presentCall` / `presentResult`，返回 provider-neutral 视图（`packages/core/tools/src/presentation.ts:46,140`）：

```ts
export type ToolCallView = GenericCallView | TerminalCallView | DiffCallView
export type ToolResultView = GenericResultView | TerminalResultView | DiffResultView
  | SearchResultView | ReadResultView | WebResultView
```

`presentation.ts:1-6` 的模块注释：

> "Tool render-intent vocabulary: the provider-neutral types a tool declares via `ToolDefinition.presentCall`/`presentResult` to say how one of its calls renders in a UI (an editor's tool-call card, a CLI log line)."

**关键收益**：前端不需要维护"工具名 → 卡片类型"的映射表。`bash` 返回 `TerminalCallView`，前端就渲染终端卡片；`read` 返回 `ReadResultView`，前端就渲染带行号的代码视图。新增工具时前端零改动。

各视图的语义（摘要）：

| 视图 | 关键字段 | 代码 |
|---|---|---|
| `TerminalCallView` | `title`(命令) / `description` / `cwd` | `presentation.ts:84-100` |
| `DiffCallView` | `title` / `diffs: FileDiff[]` / `locations` | `presentation.ts:110-118` |
| `ReadResultView` | `path` / `offset` / `lines` / `totalLines` / `lang` | `presentation.ts:281-308` |
| `SearchResultView` | `shape: 'matches'\|'paths'` + `truncated`/`total` | `presentation.ts:216-253` |
| `WebSearchResultView` | `sources: WebSource[]` / `answer` / `truncated` | `presentation.ts:355-366` |
| `WebFetchResultView` | `url` / `statusCode` / `truncated` | `presentation.ts:374-389` |

### 4.2 call/result 配对

配对键 = `callId`。运行时（`conversation-nodes/tool.ts`）：

- 调用：`rootCall`（`tool.ts:39-51`），从 `tool/call` 事件取 `callId`/`name`/`arguments`
- 结果：`rootResult`（`tool.ts:53-71`），从 `tool/result` 取 `message.source.callId` 并**回填调用头**

```ts
// tool.ts:60-62
callId: String(match.event.data.message.source.callId),
call: previous === undefined ? null : { name: previous.name, argsRaw: previous.argsRaw },
callTime: previous?.time ?? null,
```

配对失败（窗口截断）时 `call: null`，卡片仍可渲染（`tool.ts:61`）。

### 4.3 参数与结果的展示

`toolRowModel`（`ui-tool/.../models/tool-call-model.ts:211-240`）是**纯函数**，一次算出整行模型：

```ts
export function toolRowModel(toolName, block, cwd?): ToolRowModel {
  const variant = classifyTool(toolName)
  const done = 'kind' in block
  const argsRaw = (done ? block.call?.argsRaw : block.argsRaw) ?? ''
  const state: ToolRowState = !done ? 'running'
    : block.error?.code === 'interrupted' ? 'stopped'
      : block.isError ? 'error' : 'ok'
  ...
}
```

- **摘要**：按 variant 的 `SUMMARY_KEYS` 取参数（`tool-call-model.ts:142-150`），如 bash 取 `description`→`command`，read 取 `path`→`file_path`→`url`
- **展开体**：`deriveBody`（`tool-call-model.ts:191-202`），`code` variant 直接给程序体，其余给 pretty JSON
- **结果文本**：`resultText`（`tool-call-model.ts:107-117`），text 块原样、其余块 JSON，空时回退 `error.name: code`
- **失败摘要**：`errorSummary = state === 'error' && output !== null ? firstLine(output) : null`（`tool-call-model.ts:229`）

### 4.4 失败 / 中断的呈现

状态三值 + 一个特殊态（`tool-call-model.ts:20`）：

```ts
export type ToolRowState = 'running' | 'ok' | 'error' | 'stopped'
```

- `running`：行扫光动画（CSS on `data-state`），图标保留（`ToolRow.tsx:104-113`）
- `error`：`StateDot state="error"`（红点），折叠摘要换成失败首行并用错误色（`ToolRow.tsx:17-18` 注释 + `:109`）
- `stopped`：`StateDot state="warning"`（琥珀色），来自 `error.code === 'interrupted'`（`tool-call-model.ts:216`）

### 6.3 根因 2：`buildBuckets` 按类别重组，跨类时序永久丢失

`ProcessBlock.tsx:69-115`：

```ts
function buildBuckets(nodes: ProcessNode[]): Bucket[] {
  const order: BucketKey[] = []
  const map = new Map<BucketKey, BucketItem[]>()
  const push = (key: BucketKey, item: BucketItem) => {
    if (!map.has(key)) { map.set(key, []); order.push(key) }
    map.get(key)?.push(item)
  }
  for (const node of nodes) {
    if (node.kind === "thought") push("thought", {...})
    else if (node.kind === "skill") push("skill", {...})
    else if (node.kind === "note") continue
    else push(bucketFor(node.toolName), {...})   // ← 按工具名分桶
  }
  return order.map((key) => ({ key, items: map.get(key) ?? [] }))
}
```

分桶键来自 `process-display.ts:142-152`：

```ts
export function bucketFor(toolName: string): BucketKey {
  const name = (toolName ?? "").toLowerCase();
  if (name.includes("web") || name.includes("browser")) return "web";
  if (name.includes("memory")) return "memory";
  if (name.includes("knowledge") || name.includes("ontology") || name.includes("entity")) return "knowledge";
  if (name === "read" || name === "glob" || name === "grep" || name === "ls") return "explore";
  if (name === "write" || name === "edit" || name === "apply_patch") return "file";
  return "tool";
}
```

**后果**：假设真实执行是 `read a.py → edit a.py → bash test → read b.py`，渲染结果变成：

```
思考 ×N
联网搜索 ×0
调用 Skills ×0
知识库 ×0
记忆 ×0
读取文件 ×2      ← read a.py 和 read b.py 挤到一起
读取/修改文件 ×1  ← edit a.py
其他工具 ×1      ← bash test
```

**用户无法看出"先改了 a.py 才跑的测试"**。这就是用户说的"没有按执行顺序显示"。

### 6.4 根因 3：三级折叠把信息藏了两层

## ⑦ 建议的改造方案

### 7.1 总体思路

**不推翻 `ProcessNode[]` 数据结构，而是"补顺序 + 平铺渲染"。**

保留现有全部能力（记忆分档、压缩详情、终态注记、子代理树），只改三件事：

1. 给 `ProcessNode` 补 `seq` 字段（数据层）
2. 渲染从"分桶"改为"线性平铺 + 分组胶囊"（渲染层）
3. 折叠从"三级"改为"每行独立 + 一个可选的轮级总行"（交互层）

### 7.2 第一步：补顺序号（数据层，必须做）

**落点**：`frontend/src/stores/chat-store.ts`

`ProcessNode` 三个变体各加一个字段：

```ts
// 伪代码 —— 三个 interface 各加一行
export interface ProcessThoughtNode {
  ...
  seq: number        // 新增：本消息内单调递增的执行序号
}
export interface ProcessToolNode {
  ...
  seq: number        // 新增
}
export interface ProcessSkillNode {
  ...
  seq: number        // 新增
}
```

生成规则（复用已存在的 `nodes.length` 语义）：

```ts
// applyToolStart 内（chat-store.ts:1134-1144 附近）
process: [...nodes, { ..., seq: nextSeq(nodes) }]

// nextSeq 实现
function nextSeq(nodes: ProcessNode[]): number {
  return nodes.reduce((max, n) => Math.max(max, n.seq ?? 0), 0) + 1
}
```

⚠️ **迁移注意**：历史消息的 `metadata` 里存的过程节点没有 `seq`（`parseEntryProcessNodes`，`chat-store.ts:717`）。回填策略：

```ts
// parseEntryProcessNodes 里按数组下标回填
nodes.map((node, index) => ({ ...node, seq: node.seq ?? index + 1 }))
```

数组顺序本来就是事件到达顺序（`next.push`），所以下标回填是**正确的**。

**不需要改后端**：`ProcessNode[]` 的数组顺序已经是真实执行顺序，只是渲染层没用它。

### 7.3 第二步：线性平铺渲染（渲染层）

**落点**：`frontend/src/components/chat/ProcessBlock.tsx`

把 `buildBuckets` 换成 `buildRows`：

```ts
type ProcessRow =
  | { kind: "thought"; node: ProcessThoughtNode }
  | { kind: "tool"; node: ProcessToolNode; variant: ToolVariant }
  | { kind: "skill"; node: ProcessSkillNode; skill: string }
  | { kind: "note"; node: ProcessNoteNode }

function buildRows(nodes: ProcessNode[]): ProcessRow[] {
  return [...nodes]
    .sort((a, b) => (a.seq ?? 0) - (b.seq ?? 0))
    .flatMap((node): ProcessRow[] => {
      if (node.kind === "thought") return [{ kind: "thought", node }]
      if (node.kind === "skill") return node.skills.map(skill => ({ kind: "skill", node, skill }))
      if (node.kind === "note") return [{ kind: "note", node }]
      return [{ kind: "tool", node, variant: toolVariant(node.toolName) }]
    })
}
```

渲染循环（替代 `:660-662` 的 `buckets.map`）：

```tsx
{rows.map(row => {
  switch (row.kind) {
    case "thought": return <ThoughtRow key={...} node={row.node} />
    case "tool":    return <ToolRow    key={...} node={row.node} variant={row.variant} />
    case "skill":   return <SkillRow   key={...} ... />
    case "note":    return <NoteRow    key={...} node={row.node} />
  }
})}
```

**关键：`ThoughtRow` / `ToolRow` 是新拆出的单行组件，直接复用现有 `ItemStatus`、`KnowledgeItem`、`SubagentTree` 等子结构，把 `BucketRow` 里的明细行逻辑抽出来即可。**

自动折叠策略调整：
